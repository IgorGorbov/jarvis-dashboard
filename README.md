# Jarvis Dashboard

Панель наблюдения за прогонами агента Jarvis. Читает артефакты с диска, в
репозиторий агентов ничего не приносит.

## Запуск

```
yarn start
```

Открыть http://localhost:4100. При правке самой панели — `yarn dev`: перезапуск
по изменению файла средствами Node, без зависимостей.

Путь до артефактов по умолчанию — `../agents/artifacts/jarvis` относительно этого
файла. Другой путь — первым аргументом:

```
yarn start /путь/до/artifacts/jarvis
```

Переменные: `PORT` (по умолчанию 4100), `JARVIS_A2A` (по умолчанию
`http://localhost:4000`) — адрес агента для кнопки «Запустить задачу».

Зависимостей нет, сборки нет. Нужен Node 24.

## Проверки

```
yarn test
```

Два шага, оба без зависимостей:

- `node --test` — разборщики из `lib.mjs`. Там три формата исхода и две формы
  ответа агента, и `normalizeOutcome` уже один раз регрессировала: формат
  сменился с `meta.outcome` на `meta.ended`, и половина прогонов показывала
  «исход неизвестен».
- `node check-page.mjs` — компилирует скрипт из `index.html`, не исполняя его.
  Заведено после того, как конфликт имён уронил весь скрипт: панель открывалась
  пустой, без единой ошибки в интерфейсе. Проверено внесением такой ошибки —
  проверка падает с внятным сообщением.

Мокать диск и сеть незачем: тейлер журнала проверяется настоящим файлом с
недописанной строкой, это честнее мока.

## Сколько накапливается

Замер на настоящих прогонах: папка прогона 12–312 КБ (толще всего у прогонов с
несколькими попытками — логов проверок пишется по пять на попытку), журнал ~6
строк на прогон, `questions.md` ~4 КБ на разбор. На сотню прогонов выходит около
шести мегабайт. Удалять по расписанию незачем.

Что действительно не безгранично — чтение журнала целиком, поэтому при
подключении отдаётся только последние 256 КБ. Полный след давнего прогона всё
равно лежит в его папке, в `events.json`.

Если история всё же мешает, это однострочник, а не функция:

```bash
find ~/profi/agents/artifacts/jarvis -maxdepth 1 -type d -name '*-*' -mtime +30 -exec rm -rf {} +
```

Трогать нельзя `pending/` — там живое состояние: сохранённый анализ, который
ждёт подтверждения.

## Что откуда берётся

| Данные | Источник |
|---|---|
| лента событий | `events.jsonl` в корне артефактов, опрос размера раз в 500 мс, чтение хвоста с офсета |
| занят или свободен | `state.json` в корне, опрос раз в 2 с |
| список прогонов | каталоги `<runTag>-<taskRef>` плюс `runTag` из журнала (отказы на приёме папку не создают) |
| исход и ссылка на PR | `result.json`, при его отсутствии — `meta.json` / `meta.resume.json` |
| проверки, план, вопросы, диф | снимки в папке прогона |

## Как читать полосу шагов

Шагов шесть: `analyze → prepare → [implement → check → review] → pr`. Три
средних крутятся в петле, поэтому «завершился» для них не значит «пройден» —
отсюда пять состояний вместо двух.

| Вид | Значение |
|---|---|
| `analyze ✓` зелёный | пройден окончательно. Только у `analyze`, `prepare` и `pr` — они выполняются по одному разу |
| `review ◉` синий | идёт сейчас. Берётся из поля `go` последнего решения (`C2 → review`), а не угадывается по истории |
| `check ×3` серый | шаг петли выполнялся три раза и, скорее всего, выполнится снова. Счётчик стоит вместо легенды |
| `analyze ⏸` жёлтый | здесь прогон остановился и ждёт человека — вопросы или подтверждение понимания |
| `check ✕` красный | здесь прогон остановлен: решение из списка останавливающих |
| без пометки | шаг ни разу не выполнялся |

У каждого блока есть подсказка с расшифровкой — легенду держать в голове не надо.

Зелёный `pr` ставится только по решению `PR4`. Исход `PR3` («работа осталась на
ветке») к успеху не относится: PR не создан.

## Цвет полосок в списке прогонов

Цвет — это исход прогона, а не его успешность в широком смысле:

| Цвет | Исходы |
|---|---|
| зелёный | `pr` — PR создан |
| красный | `kept`, `stopped`, `failed` |
| жёлтый | `asked`, `suspended`, `no-changes`, `skipped` |
| серый | исход неизвестен: прогон идёт или оборвался без записи |

Свёрнутая задача показывает только полоски — по цвету видно, какие попытки дали
PR. Развёрнутая показывает прогоны строками, и ссылка на PR стоит в строке своего
прогона: иначе непонятно, какой PR к какому запуску.

## Управление

| Действие | Как уходит в агента |
|---|---|
| Запустить задачу | `metadata.source` плюс текст постановки |
| Ответить на вопросы | `metadata.answer`, ключ — метка задачи |
| Отменить прогон | `metadata.cancel: true` |
| Снять с ожидания | тот же `metadata.cancel` — агент сам различает активный прогон и ждущий |

Ответа на запуск ждать нельзя: `execute` в агенте синхронно дожидается всего
прогона, то есть успешный ответ пришёл бы через два часа. Панель ждёт три
секунды — за них успевает приехать только отказ или быстрый ответ отмены, — и
дальше смотрит в журнал.

Отмена работу не теряет: агент кладёт её в stash и пишет об этом в ответе,
который панель показывает как есть.

## Чего панель не умеет

- **Показывать, что происходит внутри шага.** Агент пишет событие по завершении
  шага, а не по началу: внутри `analyze` и `implement` наблюдалось до 12 минут
  полной тишины. Панель называет это «тишина N мин» и не притворяется, что
  что-то знает.
- **Разбор конверта ответа агента не проверен на живом агенте.** Текст берётся из
  `result.parts[].content.value` (и из `result.message.parts` во второй форме) по
  коду исполнителя, но не по настоящему ответу: любой пробный запрос сначала
  пишет событие приёма в журнал, поэтому безобидной проверки нет. Если после
  отмены не появилось сообщения — смотреть надо сюда.

## Форматы, которые приходится терпеть

Артефакты писались тремя разными способами, и все три лежат в каталоге:

- нынешний — `result.json` с размеченным `kind`, `meta.ended`;
- промежуточный — `meta.outcome` объектом;
- до 13 августа — `meta.outcome` строкой с человеческим текстом. Из неё
  вытаскивается только ссылка на PR, остальное помечается как «проза».
