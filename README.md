# Jarvis Dashboard

Панель наблюдения за прогонами агента Jarvis. Читает артефакты с диска, в
репозиторий агентов ничего не приносит.

## Запуск

```
yarn start
```

Открыть http://localhost:4100. При правке самой панели — `yarn dev`: перезапуск
по изменению файла средствами Node, без зависимостей.

Путь до артефактов по умолчанию — `../agents/artifacts/jarvis` относительно этого
файла. Другой путь — первым аргументом:

```
yarn start /путь/до/artifacts/jarvis
```

## Настройки

Всё необязательное, значения по умолчанию рабочие. Задаются в `.env` рядом с
панелью — она читает его сама, файла может не быть. Образец: `.env.example`.

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `JARVIS_ARTIFACTS` | каталог артефактов | `../agents/artifacts/jarvis` рядом с панелью |
| `JARVIS_A2A` | адрес агента для кнопок запуска, ответа и отмены | `http://localhost:4000` |
| `PORT` | порт панели | `4100` |
| `JARVIS_SCHEMAS` | `schemas.ts` агента — только для сверки решений и счётчика покрытия | рядом, по соседству с панелью |

Путь к артефактам можно передать и первым аргументом — он главнее `.env`, чтобы
поднять вторую панель на чужих артефактах, не трогая файл настроек:

```
yarn start /путь/до/artifacts/jarvis
```

Панель читает артефакты **с диска**, а не по сети: каталог должен быть доступен
локально — либо панель стоит на машине агента, либо каталог смонтирован. Своей
аутентификации у неё нет: кто открыл порт, тот управляет агентом. На `localhost`
это безопасно, наружу — только за прокси с авторизацией или в VPN.

Зависимостей нет, сборки нет. Нужен Node 24.

## Проверки

```
yarn test
```

Два шага, оба без зависимостей:

- `node --test` — разборщики из `lib.mjs`. Там три формата исхода и две формы
  ответа агента, и `normalizeOutcome` уже один раз регрессировала: формат
  сменился с `meta.outcome` на `meta.ended`, и половина прогонов показывала
  «исход неизвестен».
- `node check-page.mjs` — компилирует скрипт из `index.html`, не исполняя его.
  Заведено после того, как конфликт имён уронил весь скрипт: панель открывалась
  пустой, без единой ошибки в интерфейсе. Проверено внесением такой ошибки —
  проверка падает с внятным сообщением.
- `node check-ids.mjs` — сверяет с источником и решения (`DecisionId`,
  `IncomingId`), и виды исхода. Этот класс ошибки кусал четырежды: `PR3`, `I5`,
  `A1`, потом исход `awaiting-confirmation`. Если репозитория агентов рядом нет,
  проверка пропускается.

- `node coverage.mjs --short` — сколько сценариев конвейера видели живьём.
  Не роняет ничего: полного покрытия не будет никогда, часть веток живёт только
  в Mattermost, часть срабатывает лишь на браке модели. Это отчёт, а не ворота.

## Что ещё не проверяли

```
yarn coverage
```

Печатает решения агента, которых не было ни на одном прогоне, и рядом — задачу,
которой дыру закрывают, готовую к вставке в поле «Запустить задачу».

Список решений берётся из схем агента, увиденное — из ленты, наблюдения копятся
в `coverage.json`: каталог артефактов чистят, и без накопления счёт обнулялся бы
вместе с ним. Новое решение агента, которому не завели сценарий в
`scenarios.json`, печатается отдельной строкой — иначе про него никто не
вспомнит, потому что его нет ни в одном списке.

Разбор сценариев и порядок прогона — в `~/profi/docs-solutions/jarvis-test-map.md`.

## Редкие состояния, которых ждать месяцами

```
node fixtures.mjs && node dash.mjs fixtures/artifacts
```

Собирает поддельный каталог артефактов с состояниями, которых на живых прогонах
не было: упавший агент, оборванная работа с патчем, упор в срок прогона,
провал установки зависимостей, ожидание ответа в треде Mattermost. Время в
подделке фиксированное — два запуска дают одинаковый результат.

Подделка проверяет **отрисовку**, а не поведение агента: сами ветки конвейера
закрываются задачами из `yarn coverage` и модульными тестами на чистые функции
решений в репозитории агентов. Каталог не коммитится, он собирается за секунду.

Мокать диск и сеть незачем: тейлер журнала проверяется настоящим файлом с
недописанной строкой, это честнее мока.

## Сколько накапливается

Замер на настоящих прогонах: папка прогона 12–312 КБ (толще всего у прогонов с
несколькими попытками — логов проверок пишется по пять на попытку), журнал ~6
строк на прогон, `questions.md` ~4 КБ на разбор. На сотню прогонов выходит около
шести мегабайт. Удалять по расписанию незачем.

Что действительно не безгранично — чтение журнала целиком, поэтому при
подключении отдаётся только последние 256 КБ. Полный след давнего прогона всё
равно лежит в его папке, в `events.json`.

Если история всё же мешает, это однострочник, а не функция:

```bash
find ~/profi/agents/artifacts/jarvis -maxdepth 1 -type d -name '*-*' -mtime +30 -exec rm -rf {} +
```

Трогать нельзя `pending/` — там живое состояние: сохранённый анализ, который
ждёт подтверждения.

## Что откуда берётся

| Данные | Источник |
|---|---|
| события прогона | `events.jsonl` в корне артефактов, опрос размера раз в 500 мс, чтение хвоста с офсета |
| ходы и вызовы инструментов | `trace.jsonl` папки прогона: строки `{tool}` — вызовы, `{turn}` — маркеры хода. Счётчик живой, опрос раз в 3 с у идущего прогона |
| занят или свободен | `state.json` в корне, опрос раз в 2 с |
| список прогонов | каталоги `<runTag>-<taskRef>` плюс `runTag` из журнала для запусков и отказов на приёме — у тех папки нет. Ответ и запрос отмены приезжают своими A2A-запросами и получают свои метки, но прогонами не являются: показываются в ленте того прогона, к которому относятся |
| исход и ссылка на PR | `result.json`, при его отсутствии — `meta.json` / `meta.resume.json` |
| проверки, план, вопросы, диф | снимки в папке прогона |

## Шаги, попытки, ходы

Три вложенных счёта, и путать их легко:

| Что | Сколько | Где видно |
|---|---|---|
| **Шаг** | шесть на прогон: `analyze`, `prepare`, `implement`, `check`, `review`, `pr` | верхняя полоса |
| **Попытка** | круг петли `implement → check → review`, предел общий на прогон | счётчик в скобке петли и `×N` у шагов |
| **Ход** | обмен модели с инструментами внутри шага; предел свой у каждого шага и приходит в `turnLimit` события старта — зашивать его нельзя, у анализа он уже менялся с 80 на 120 | вторая полоса бюджета: «шаг analyze: 57 из 120 ходов» |

На вкладке «Инструменты» время стоит только у вызовов дольше секунды: медиана
вызова — 26 мс, две трети короче 100 мс, и в секундах это был столбец «0.0 с».
Общее время ушло в шапку списка.

Замер: ход занимает 30–60 секунд, поэтому счётчик ходов меняется примерно дважды
в минуту. Признак жизни — не он, а текущий вызов инструмента справа от шагов:
вызовов в 1,7 раза больше, чем ходов.

## Как читать полосу шагов

Шагов шесть: `analyze → prepare → [implement → check → review] → pr`. Три
средних крутятся в петле, поэтому «завершился» для них не значит «пройден» —
отсюда пять состояний вместо двух.

| Вид | Значение |
|---|---|
| `analyze ✓` зелёный | пройден окончательно. Только у `analyze`, `prepare` и `pr` — они выполняются по одному разу |
| `review ◉` синий | идёт сейчас. Берётся из поля `go` последнего решения (`C2 → review`), а не угадывается по истории |
| `check ×3` серый | шаг петли выполнялся три раза и, скорее всего, выполнится снова. Счётчик стоит вместо легенды |
| `analyze ⏸` жёлтый | здесь прогон остановился и ждёт человека — вопросы или подтверждение понимания |
| `check ✕` красный | здесь прогон остановлен: решение из списка останавливающих |
| без пометки | шаг ни разу не выполнялся |

У каждого блока есть подсказка с расшифровкой — легенду держать в голове не надо.

Справа от шагов, пока прогон идёт, стоит текущий вызов инструмента —
`Grep · …/useOrderScreenRenderCalc.ts`. Если и трасса молчит дольше двух минут,
вместо него «тишина N мин». Полный список вызовов — на вкладке «Инструменты».

Зелёный `pr` ставится только по решению `PR4`. Исход `PR3` («работа осталась на
ветке») к успеху не относится: PR не создан.

## Цвет полосок в списке прогонов

Цвет — это исход прогона, а не его успешность в широком смысле:

| Цвет | Исходы |
|---|---|
| зелёный | `pr` — PR создан |
| красный | `kept`, `stopped`, `failed` |
| жёлтый | `asked`, `suspended`, `no-changes`, `skipped` |
| серый | исход неизвестен: прогон идёт или оборвался без записи |

Список прогонов — 240 px: строке с меткой, датой и ссылкой на PR нужно около
197 px содержимого, на 210 дата заезжала под ссылку. `.run` при этом переносит,
а не подрезает — если панель сузить, ссылка уйдёт на вторую строку, но ничего не
пропадёт.

Свёрнутая задача показывает только полоски — по цвету видно, какие попытки дали
PR. Развёрнутая показывает прогоны строками, и ссылка на PR стоит в строке своего
прогона: иначе непонятно, какой PR к какому запуску.

## Управление

| Действие | Как уходит в агента |
|---|---|
| Запустить задачу | `metadata.source` плюс текст постановки |
| Продолжить с разбором | `metadata.understandingConfirmed: true` |
| Ответить на вопросы | `metadata.answer`, ключ — метка задачи |
| Отменить прогон | `metadata.cancel: true` |
| Снять с ожидания | тот же `metadata.cancel` — агент сам различает активный прогон и ждущий |

Оба случая, когда агент ждёт человека, показываются блоком над лентой: вопросы —
с полем ответа, пересказ — с кнопкой «Подтвердить понимание», которая сама
перезапускает задачу с сохранённым разбором. Прогон при этом красным не
красится: он не сломался, а ждёт, и цвет берётся по последнему решению, а не по
исходу — исход `stopped` слишком крупный, под ним и «проверки красные», и
«подтверди понимание».

Запуск из панели двухшаговый. Первый разбирает задачу и останавливается на
пересказе «как я понял задачу» (решение `A5`), сохранив разбор. Второй — тот же
текст с галочкой «продолжить с сохранённым разбором» — берёт сохранённое и идёт
в реализацию. Галочка на первом запуске даёт `A1` и потраченный впустую прогон:
сохранять ещё нечего. Из Mattermost этого шага нет, там подтверждение не
запрашивается.

Ответа на запуск ждать нельзя: `execute` в агенте синхронно дожидается всего
прогона, то есть успешный ответ пришёл бы через два часа. Панель ждёт три
секунды — за них успевает приехать только отказ или быстрый ответ отмены, — и
дальше смотрит в журнал.

### Протокол

Снято с живого агента, потому что угадать не получилось:

- заголовок **`A2A-Version: 1.0`** обязателен. Без него сервер считает версию
  запроса `0.3` и отбивает его целиком;
- метод JSON-RPC — **`SendMessage`**, а не `message/send`;
- часть сообщения — **`parts[].text`** в обе стороны. Форма `content.$case` это
  внутренний вид SDK: сервер такой конверт принимает молча, но текст теряет —
  агент получал пустую задачу, `issue.txt` выходил нулевой длины;
- JSON-RPC заворачивает ответ в `result`, REST (`POST /a2a/rest/v1/message:send`)
  отдаёт сообщение без обёртки.

Ошибка протокола теперь показывается как ошибка. До этого неверный конверт
выглядел успешной отправкой: панель говорила «отправлено», а до агента не
доходило ничего.

Отмена работу не теряет: агент кладёт её в stash и пишет об этом в ответе,
который панель показывает как есть.

## Чего панель не умеет

- **Показывать текст модели.** Видно, что агент делает — какие файлы читает и
  правит, — но не то, о чём он при этом думает. Для этого нужен переход с
  `generate()` на `stream()` в самих агентах.

- **Отмена на стадии реализации не проверена.** Управление проверено на живых
  прогонах целиком: запуск с настоящей постановкой, ответ на вопросы, отмена
  идущего прогона, снятие с ожидания. Не проверено обещание «работа сохранится в
  stash» — для него нужен прогон, дошедший до правок в клоне, а пробные задачи
  до этого не доходили.

## Форматы, которые приходится терпеть

Артефакты писались тремя разными способами, и все три лежат в каталоге:

- нынешний — `result.json` с размеченным `kind`, `meta.ended`;
- промежуточный — `meta.outcome` объектом;
- до 13 августа — `meta.outcome` строкой с человеческим текстом. Из неё
  вытаскивается только ссылка на PR, остальное помечается как «проза».
