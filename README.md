# Jarvis Dashboard

Панель наблюдения за прогонами агента Jarvis: что он делает прямо сейчас, чем
кончились прошлые запуски, и кнопки запустить / ответить / отменить.

Читает артефакты с диска, в репозиторий агентов ничего не приносит.
Зависимостей нет, сборки нет. Нужен Node 24.

```
yarn start          # http://localhost:4100
yarn dev            # то же с перезапуском по изменению файла
```

## Настройки

Всё необязательно. Задаются в `.env` рядом с панелью — она читает его сама,
файла может не быть. Образец: `.env.example`.

| Переменная | Что задаёт | По умолчанию |
|---|---|---|
| `JARVIS_ARTIFACTS` | каталог артефактов | `../agents/artifacts/jarvis` рядом с панелью |
| `JARVIS_A2A` | адрес агента для кнопок | `http://localhost:4000` |
| `PORT` | порт панели | `4100` |
| `JARVIS_SCHEMAS` | `schemas.ts` агента — только для двух проверок ниже | рядом, по соседству |

Путь к артефактам можно передать первым аргументом — он главнее `.env`:
`yarn start /путь/до/artifacts/jarvis`.

Панель читает артефакты **с диска**, а не по сети: каталог должен быть доступен
локально. Своей аутентификации у неё нет — кто открыл порт, тот управляет
агентом. На `localhost` это безопасно, наружу — только за прокси с авторизацией.

## Что откуда берётся

| Данные | Источник |
|---|---|
| лента событий | `events.jsonl` в корне: опрос размера раз в 500 мс, дочитывание хвоста по офсету, раздача в браузер потоком |
| занят или свободен, срок прогона, ждущие ответа | `state.json` в корне, опрос раз в 2 с |
| всё про прогон: модель, сессии, анализ, проверки, ревью, исход | `run.jsonl` в папке прогона, строка на факт |
| ходы и вызовы инструментов | `trace.jsonl` в папке прогона, опрос раз в 3 с у идущего прогона |
| диф | `diff.aborted.patch` либо `diff.final.patch` |

Накапливается мало: папка прогона — около двух килобайт, чистить по расписанию
незачем. Единственное безграничное место — общая лента, поэтому при подключении
отдаётся только последние 256 КБ.

Трогать нельзя `pending/` — там сохранённый анализ, который ждёт подтверждения.

## Проверки

```
yarn test
```

Четыре шага, все без зависимостей:

- **`node --test`** — разборщики `run.jsonl` и ответов агента. Проверены порчей:
  восемь поломок из восьми ловятся.
- **`check-page.mjs`** — компилирует скрипт из `index.html`, не исполняя.
  Заведён после того, как конфликт имён уронил весь скрипт и панель открылась
  пустой, без единой ошибки на экране.
- **`check-ids.mjs`** — сверяет решения агента (`DecisionId`, `IncomingId`) и
  виды исхода со `schemas.ts`. Этот класс ошибки кусал четырежды: новое решение
  панель молча красила зелёным.
- **`coverage.mjs --short`** — сколько сценариев конвейера видели живьём. Отчёт,
  а не ворота: полного покрытия не будет никогда, часть веток живёт только в
  Mattermost, часть срабатывает лишь на браке модели.

Две последние пропускаются, если схем агента рядом нет.

### Чем закрыть непокрытое

```
yarn coverage
```

Печатает решения, которых не было ни на одном прогоне, и рядом — задачу, готовую
к вставке в поле «Запустить задачу». Задачи берутся из `scenarios.json`; файл
локальный, в git его нет. Без него покрытие считается как обычно, но подсказать
нечем. Формат — объект «решение → `когда` / `задача` / `как`».

### Редкие состояния, которых ждать месяцами

```
node fixtures.mjs && node dash.mjs fixtures/artifacts
```

Поддельный каталог с тем, чего на живых прогонах почти не бывает: упавший агент,
оборванная работа с патчем, упор в срок, провал установки зависимостей, ожидание
ответа в треде. Проверяет отрисовку, а не поведение агента; время фиксированное,
два запуска дают одинаковый результат.

## Как читать полосу шагов

Шагов шесть: `analyze → prepare → [implement → check → review] → pr`. Три
средних крутятся в петле, поэтому «завершился» для них не значит «пройден» —
отсюда пять состояний вместо двух.

| Вид | Значение |
|---|---|
| `analyze ✓` зелёный | пройден окончательно. Только у `analyze`, `prepare` и `pr` — они выполняются по разу |
| `review ◉` синий | идёт сейчас: у шага стартов больше, чем завершений |
| `check ×3` серый | шаг петли выполнялся три раза и, скорее всего, выполнится снова |
| `analyze ⏸` жёлтый | прогон ждёт человека: вопросы, подтверждение понимания или отмена |
| `check ✕` красный | здесь прогон остановлен |
| без пометки | шаг ни разу не выполнялся |

У каждого блока есть подсказка — легенду держать в голове не надо.

Справа, пока прогон идёт, стоит текущий вызов инструмента: `Grep · …/foo.ts`.
Если и трасса молчит дольше двух минут — «тишина N мин». Полный список вызовов
на вкладке «Инструменты».

Зелёный `pr` ставится только по решению `pr-opened`. `kept-on-branch` — работа
осталась на ветке, PR не создан, к успеху не относится.

## Цвет полосок в списке

Цвет — это исход прогона, а не успешность в широком смысле:

| Цвет | Исходы |
|---|---|
| зелёный | `pr` |
| красный | `kept`, `stopped`, `failed` |
| жёлтый | `asked`, `cancelled`, `awaiting-confirmation`, `no-changes` |
| серый | исход неизвестен: прогон идёт или оборвался без записи |

Свёрнутая задача показывает только полоски, развёрнутая — прогоны строками, и
ссылка на PR стоит в строке своего прогона: иначе непонятно, какой PR к какому
запуску.

## Управление

| Действие | Как уходит в агента |
|---|---|
| Запустить задачу | `metadata.source` плюс текст постановки |
| Продолжить с разбором | `metadata.understandingConfirmed: true` |
| Ответить на вопросы | `metadata.answer`, ключ — метка задачи |
| Отменить прогон либо снять с ожидания | `metadata.cancel: true` — агент сам различает |

Запуск двухшаговый: первый прогон разбирает задачу и останавливается на пересказе
«как я понял задачу», сохранив разбор; второй — тот же текст с галочкой — берёт
сохранённое и идёт в реализацию. Галочка на первом запуске даёт отказ: сохранять
ещё нечего.

Ответа на запуск ждать нельзя — агент синхронно дожидается всего прогона, то есть
успешный ответ пришёл бы через два часа. Панель ждёт три секунды, за них успевает
приехать только отказ, дальше смотрит в журнал.

### Протокол

Снято с живого агента, потому что угадать не получилось:

- заголовок **`A2A-Version: 1.0`** обязателен — без него сервер отбивает запрос;
- метод JSON-RPC — **`SendMessage`**, а не `message/send`;
- часть сообщения — **`parts[].text`** в обе стороны. Форма `content.$case` это
  внутренний вид SDK: сервер такой конверт принимает молча, но текст теряет —
  агент получал пустую задачу.

Ошибка протокола показывается как ошибка. До этого неверный конверт выглядел
успешной отправкой: панель говорила «отправлено», а до агента не доходило ничего.

## Чего панель не умеет

**Показывать текст модели.** Видно, что агент делает — какие файлы читает и
правит, — но не то, о чём он при этом думает. Для этого нужен переход с
`generate()` на `stream()` в самих агентах.
